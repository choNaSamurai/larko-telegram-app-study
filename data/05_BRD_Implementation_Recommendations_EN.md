## 🔐 1. Security & Authorization (Telegram Auth)

> [!IMPORTANT]
> **Status:** Recommended for implementation in the next sprint to move beyond simple LocalStorage identification.

### Description
Currently, the application identifies users via `telegram_id` stored in `localStorage` without server-side verification. To ensure data integrity and prevent spoofing, a robust validation mechanism for Telegram `initData` must be implemented once a backend is integrated.

### Business Requirements
1. **InitData Validation:**
   - Implement a server-side validation method (e.g., Supabase Edge Functions) to verify the `hash` from Telegram `initData`.
   - Use the secure `BOT_TOKEN` and the constant `"WebAppData"` for verification.
   - Algorithm: HMAC-SHA256.

2. **Transition from LocalStorage to Session Sync:**
   - Once validated, create/update a user session in the backend.
   - Replace manual `telegram_id` checks with valid JWT-based authentication.

3. **Row Level Security (RLS):**
   - Configure security policies in backend tables (`orders`, `time_logs`, `advances`) to ensure users can only access their own data via `auth.uid()`.

## 💾 2. Current Storage Strategy (LocalStorage Optimization)

> [!IMPORTANT]
> **Status:** High Priority for robust offline development and autonomous testing.

### Description
Since the application currently relies on `localStorage` for all operations (due to the absence of a live Supabase connection in dev/testing environments), the existing implementation must be optimized for reliability and potential migration.

### Business Requirements
1. **Storage Switcher:**
   - Maintain the `IS_DEV` / `USE_LOCAL_STORAGE` toggle in `dataService.ts`.
   - Ensure all CRUD operations are performed against `localStorage` when the toggle is active.

2. **Data Persistence & Initialization:**
   - Initialize `localStorage` with base mock data on first launch if empty.
   - Ensure immediate write-through for all changes (new orders, balance updates, time logs).

3. **Asynchronous Interface Simulation:**
   - All `dataService` methods (e.g., `getOrders`, `createOrder`, `updateStatus`) must return Promises to simulate network latency, preventing UI "jumps" when switching to a real API later.
